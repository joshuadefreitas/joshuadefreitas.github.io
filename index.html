trace-npm

Supply chain forensics

npm now asks you to approve install scripts. Nothing tells you what they do. trace-npm runs one under a syscall tracer and reports what it read, spawned and contacted — including the planted credential it took the bait on.

npx trace-npm run --package suspect --script postinstall

Does not establish that a package is safe. Evidence, not verdicts — and the report lists what it could not see.

How I work

Make the invisible legible.

The hard part is rarely choosing a model. It’s shaping everything around it so the result can be trusted, tested, and handed over without a long note explaining which parts to ignore.

01Start with the boundary

Define the data contract, the consumer, and the evidence. Complexity comes later, if at all.

02Make behaviour observable

Reproducible runs, explicit decisions, and results someone can inspect without taking my word for any of it.

03Earn the abstraction

The first system should be narrow enough to be right. Depth comes when the evidence demands it.

The standard

Seven rules. Each one used to be a bug.

Principles are cheap — you can hold any of them for free. These each cost something, so the receipt is printed underneath. Every incident below comes from my own open-source projects, where the only thing at stake was my own time. It is a list of times I was wrong, arranged to look like expertise.

  1. 01

    Enforced, not documented

    A property that is described but not checked by a machine is not a property. It is an intention.

    Cost Seven test files guarding a bit-exact contract, all gated behind an environment variable set precisely nowhere. They passed for months by never running. Elsewhere, a drift check that passed by comparing an empty folder with itself, which it did flawlessly.

  2. 02

    Fixtures come from reality

    Generated by running the real thing and committing what it produced — never hand-authored to match what the implementation expects.

    Cost Four defects shipped green because I wrote the fixtures to match what I believed the parser did. Fixture and parser agreed with each other completely. They were both wrong in the same direction, which is the worst possible kind of agreement.

  3. 03

    The builder does not verify its own work

    Verification means running it and reading the output, not reading the diff. The verifier should lack the ability to change the code. The asymmetry is the point.

    Cost Nine of twenty-two defects in a first release existed only in the gap between “I ran it” and running it.

  4. 04

    Loss must be visible

    Anything dropped, filtered, skipped or approximated is counted and surfaced. Silent filtering is the defect; disclosed filtering is a feature.

    Cost Seventeen percent of a trace quietly discarded. No number anywhere admitted it, so for a while it looked like a very clean trace.

  5. 05

    State the limits where the output is read

    The README is not where limits belong, because output gets pasted into issue threads and chat windows, detached from the repo that explains it. Every artifact has to carry its own.

    Cost Every limitation was written down, in the README, where it stayed. The output travelled on its own and read as a clean result.

  6. 06

    Know which direction failure runs

    Missing something is bad. Confidently reporting absence when something happened is disqualifying, because the reader acts on it.

    Cost A credential theft that worked, reported as (failed), because a non-blocking socket returns -1 EINPROGRESS. Impeccable at the syscall level. A lie everywhere it was going to be read.

  7. 07

    Claims are scoped to what was tested

    “Verified” names the environment: which platform, which backend, which version. If it was checked against one implementation, the claim is about that implementation.

    Cost Bit-exact parity claimed in general, having been observed on exactly one graphics backend. It later held on a second one too — which was luck wearing the costume of rigour.

Reviewed quarterly. Any rule I didn’t actually follow gets enforced or deleted, because a standard nobody follows is just a list of things you admire from a distance — and admiring a check is not the same as running one.
